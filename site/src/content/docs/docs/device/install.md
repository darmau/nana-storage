开着设备端处理时，上传的照片（缩略图、预览、指纹、人脸、视频转码）由**你自己的电脑**处理，**不启动 Cloudflare 容器**，也就不产生容器费用。它用的是和云端完全相同的处理代码和模型（同一个 Dockerfile），结果一致。

适合：一次导入几千、几万张照片；或者干脆一直开着，让家里的电脑负责所有处理。

## 安装

需要 Docker Desktop。在 Docker 的 设置 › Resources 里给它尽量多的 CPU 和内存，每个并行任务可能用 1–2 GB 内存。

```bash
cd apps/device
docker compose up -d --build
```

如果云端关闭了人脸识别（`NANA_FACES=off`），这里也要用同样的值构建：

```bash
NANA_FACES=off docker compose up -d --build
```

## 登录与接管

打开 <http://localhost:7878>：

1. 第一次会自动打开设置（右上角的齿轮）：填相册地址（比如 `https://photos.example.com`）、设备名称、并行任务数（默认是 Docker 可用 CPU 的 3/4，内存紧张时调低）。
2. 点“登录”，在浏览器里打开它给出的链接，用你平时登录相册的方式（Cloudflare Access 邮箱验证码）登录。凭证保存在 Docker 卷里，过期时界面会提示。
3. 登录后自动接管。之后像平常一样在浏览器里上传，排队的任务都由这台电脑处理。相册的 设置 › 后台处理 会显示是哪台设备在处理。

启动时会先自检（模型可读、vips / exiftool / ffmpeg 可用），通过了才接管。

## 停止

- `docker compose stop`，或者在界面里点“交还云端”。手上正在处理的任务会退回服务器，云端容器重新接手。
- 电脑关机或断网时，大约 **2 分钟**后服务器自动改回云端容器；接管期间留下的任务由每小时的定时任务补发。
- 连续失败 5 次会自动交还云端（多半是本机环境有问题）。

## 它是怎么工作的

- **身份**：用你自己的 Access 登录（`cloudflared`），和浏览器一样。服务器没有为它开任何额外的账号、令牌或后门。
- **接管**：每次认领任务都会续一个 2 分钟的租约。租约有效时，服务器的队列消费者不启动容器，任务留在数据库里等这台电脑来认领。空闲时每 10 秒问一次，一直开着每天约 8640 次请求，费用可以忽略。
- **处理**：下载原件 → 本机处理 → 把缩略图、预览、H.264 预览上传到服务器指定的位置 → 服务器用和容器路径**完全相同**的代码写数据库。处理期间照片被改过（比如旋转了），服务器会发现结果过时，重新处理，不会写错。
- **失败**：和容器一样，每个任务最多尝试 3 次。
- **熔断**：设备的任务同样受[熔断](../../costs/)约束（同一张照片反复处理）；熔断时设备不能接管。设备的处理时长不计入容器费用。

## 架构差异

Cloudflare 的镜像是 linux/amd64，Apple Silicon 的 Mac 上是 arm64。感知哈希完全一致，CLIP 向量的余弦相似度约 0.99（高于所有阈值），两边处理的照片混在一起没有问题。

## 升级

每次更新相册之后，在 `apps/device` 下重新构建：

```bash
docker compose up -d --build
```

CHANGELOG 里标了“用设备端处理的需要操作”的版本尤其要重建，否则新功能（比如裁切、打码）在设备上处理会失败（不会写入错误的结果）。
